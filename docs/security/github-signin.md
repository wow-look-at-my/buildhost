# Browser sign-in with GitHub (per-repo authorization)

Extracted verbatim from CLAUDE.md. Paragraph breaks go at the existing topic boundaries. No wording changed. CLAUDE.md carried this bullet TWICE, in two versions that had drifted apart. The older copy predated the dead-token re-auth path. The newer, superset version is what follows. The stale copy is dropped.

## The flow

A browser that hits a private resource (a private static-site PR preview or download) used to get a raw JSON `401` with no way to authenticate. GitHub login turns that into a sign-in. It is configured with `BUILDHOST_GITHUB_CLIENT_ID` and `BUILDHOST_GITHUB_CLIENT_SECRET`. `requireProject`'s `unauthorizedResponse` (`internal/auth/middleware.go`) then `303`-redirects a **browser navigation** (`Accept: text/html`) that carries no token. The target is the apex `/__signin?next=<full original URL>`, which runs the GitHub OAuth Authorization Code flow (`internal/auth/githublogin.go`). `handleSigninStart` sets a short-lived signed-state cookie and a CSRF nonce cookie. It redirects to GitHub with `scope=repo`, the only classic OAuth scope that grants private-repo visibility. The access check below needs that visibility. `handleSigninCallback` answers on the fixed `redirect_uri`. It verifies the state and the nonce, exchanges the code for a user token, and reads the user's login (`GET /user`).

## Callback failures are never dead ends

The browser is parked on the fixed callback URL. A reload there re-submits the consumed single-use code. So every failure branch logs through `slog`, GitHub's `error` and `error_description` from a failed exchange included. It never logs a code, a token or a secret. A *recoverable* failure `303`s back to `/__signin?retry=1&next=<the state's own MAC-verified next>` and restarts the flow. Expired state is one such failure. A nonce cookie that is missing or mismatched is another (a second sign-in tab overwrites it). The `retry` marker rides the **signed state** (`signinState.retried`). A restarted flow that fails again therefore renders the terminal page instead of a loop. The marker never relaxes any validation.

Terminal failures render a small `signinFailedHTML` 4xx page. They are forged or corrupt state, GitHub's `?error=`, a failed code exchange, and a failed `GET /user`. The page carries one sanitized sentence and a "Try signing in again" link to `/__signin` with the verified next. Forged state leaves out the next. The page is **never a 5xx**. Cloudflare replaces an origin 5xx body with its own bare error page. That used to strand users at the callback with `error code: 502` and nothing in the logs. Validation semantics stay as they were: state MAC and expiry, the double-submit nonce, and `safeNextURL`.

## The session cookie

It mints a buildhost-signed `bh_session` cookie that carries **login and the GitHub token**. The MAC is an HMAC over `login\x00token|exp` with the shared `download-signing.key`. The cookie is HttpOnly, SameSite=Lax, Secure on https, and lives 12h. It is set **domain-wide** (`Domain=<apex>`), so one login on the single apex callback works across every service subdomain.

## Authorization is per-repo, not an org allowlist

Each project records the GitHub `owner/repo` it was provisioned from. The field is `projects.github_repo`, set from the OIDC publish subject `repo:OWNER/NAME:...` through `WithOIDCRepo` on create. Each write re-syncs it. `Authenticate` verifies `bh_session` and puts `WithUser(login)` and `WithGitHubToken` on the request. `requireProject` then calls `userCanReadProject`. That grants read only when the signed-in user can reach the repo. The probe is `GET /repos/{owner}/{repo}` with the user's token, and access means a `200` (`canAccessRepo`, cached per login, repo and token-fingerprint for 5m).

`checkRepoAccess` classifies the probe three ways. A `200` is access. A `404` is a definite no, because GitHub 404s a repo the token cannot see. A `401` means **the session's embedded token itself is dead**, revoked or expired mid-session. On this fixed-host authenticated GET, rate limiting answers 403 or 429 and never 401. A 401 is therefore unambiguous.

The cache stores **only authoritative answers**: 200, 404, and the token-dead 401. A dead token never comes back, and the fingerprint key re-checks a fresh sign-in. A *transient* failure therefore denies the one request and is not cached. A network error, a 5xx, a 429 and a rate-limit 403 are all transient. Caching one pins an authorized owner to "Access denied" for a whole TTL over a momentary GitHub hiccup. The token fingerprint in the key does the matching job for a re-login. A broader-scoped token is never shadowed by a negative answer cached against the previous token. Every probe outcome other than 200 and 404 logs at WARN with the repo and the status.

This applies to ReadAccess and HiddenReadAccess. It never grants write, which still needs a `write` token. A project with no recorded `github_repo` cannot be opened through GitHub login at all. A token is the only way in.

## A dead session token re-auths transparently

The access probe answers the token-dead `401`. The ReadAccess deny path then marks the request with `WithSessionTokenDead`. `unauthorizedResponse` clears the `bh_session` cookie through `clearCookie`. `apexHost` strips a known service label there, so the clear's Domain matches the apex Domain the cookie was set with, even from a service subdomain. The browser then gets a `303` to `/__signin?next=<original URL>`. That is loop-safe, because the OAuth callback mints a session only after `GET /user` succeeds with the fresh token. A 401 used to go in the transient bucket. A browser whose 12h cookie outlived its GitHub token was then dead-ended on a misleading "Access denied" page until sign-out. Hidden reads (`HiddenReadAccess`) keep the canonical 404 even for a dead session. A re-auth redirect there leaks that the hidden project exists.

## A signed-in but unauthorized browser gets an actionable 403

**A signed-in browser that is still unauthorized with a live token** is NOT redirected. Its GitHub account cannot read the backing repo, or the project has no `github_repo`. It already holds a valid session, so a `/__signin` bounce loops, because GitHub re-auths the same account. `unauthorizedResponse` renders an actionable HTML `403` instead (`signedInForbiddenHTML`). The page names the repo access the resource needs. It offers a "Sign out & switch account" link to the apex `/__signout?next=<resource>` through `signoutURL`. The user re-authenticates as an account that has access. That replaces a dead-end JSON `401` no browser can act on. The resolved project goes into the request context before the access switch. The page can then name the repo. The page relaxes CSP to `default-src 'none'` plus `style-src 'unsafe-inline'` for one inline `<style>`. It runs no scripts.

`safeNextURL` accepts only a same-site path, or an apex or subdomain URL. There is no open redirect. `apexRootURL` derives the apex by a strip of a known service label. The whole flow is apex-only (`/__signin`, `/__signin/callback` and `/__signout`, through `HandleRaw`), because GitHub OAuth registers a single callback URL. An unconfigured server falls a browser back to the plain JSON `401`. Programmatic clients and `/v2/` OCI never change. A public site (`X-Public-Site: true`) is still served with no auth at all.

## Setup

Create a GitHub OAuth App with the callback `https://{apex}/__signin/callback`. Set `BUILDHOST_GITHUB_CLIENT_ID` and `BUILDHOST_GITHUB_CLIENT_SECRET`. There is a trade-off. The `repo` scope is broad, and the user's token lives in the signed session cookie. A GitHub App with a fine-grained read-only repo permission narrows that, and it is future work.

## Cross-domain sign-in handoff (site domain)

`myapp.<site-domain>` is a different REGISTRABLE domain from the primary apex. The `Domain=<apex>` `bh_session` cookie therefore cannot cross to it. The single OAuth App's callback also lives on the primary apex only. An unauthenticated site-domain browser gets a 303 to `https://<BUILDHOST_PRIMARY_DOMAIN>/__signin?next=<original URL>`. With no primary domain configured it gets the plain JSON 401 instead, never a redirect to an apex that cannot complete OAuth.

Sign-in there is a full OAuth round trip. It completes at once when the request already carries a valid primary-apex session. The server then parks the minted session VALUE under a random one-time nonce (`ssoHandoffs`, in memory, TTL-swept). A restart voids the in-flight codes harmlessly. The browser gets a 303 to `https://<next-host>/__sso?code=<signed nonce+next>&next=<original>`. The code is HMAC-signed with the shared `download-signing.key`, purpose-separated. It expires in 60s or less. A redemption deletes it, so it is single-use. It also BINDS the destination, and a mismatched `next` query parameter is rejected. **The session token itself never appears in any URL.** The code is worthless without the server-side entry. Tests assert that: no token material reaches any Location header.

`/__sso` answers only on the site domain. Its own Host gate 404s elsewhere, and the host-agnostic registration exists only for the bare site apex fallthrough. It sets the parked session as a `Domain=<site-domain>` cookie through the same `setSessionCookie` (`apexHost` classifies a site host to the site apex). It then 303s to the destination. Every handoff response is `Cache-Control: no-store`. Every failure is a 4xx page with a restart link at the primary apex (`signinFailedPage`, shared with the callback), and never a 5xx.

Consider the cross-site theft shapes. A crafted signin link to an attacker's public project site signs only the VICTIM's own browser into the site domain. The cookie is HttpOnly and page JS cannot read it. Site responses use `Access-Control-Allow-Origin: *`, which a browser never combines with credentials, so a cross-origin credentialed read stays blocked. That is the trust shape arbitrary site JS on `sites.<apex>` already has under the apex-wide cookie.

## Unknown-domain exposure (scoped to the primary apex when configured)

With `BUILDHOST_PRIMARY_DOMAIN` set, the web frontend (`/`, `/projects/*`, `/_ui/style.css`) and the WHOLE `/api/v1` surface answer only on that apex. They register through `auth.HandlePrimary` and `auth.HandleRawPrimary` (internal/auth/registry.go). The `primaryOnly` gate there compares the port-stripped, case-folded request Host against the configured apex. Any other unclaimed host gets the router's own `http.NotFound`. The gate runs BEFORE requireProject, so no auth semantics run off-apex at all: no 401, no sign-in redirect, no OIDC auto-provisioning. The 404 is byte-identical to the one for a genuinely unregistered path, so there is no "buildhost but wrong host" fingerprint. `TestPrimaryDomain_ScopesWebAndAPIToApex` pins that.

Some routes stay host-agnostic on every unclaimed host, the bare site apex and a stray CNAME included. They are `/healthz` and `/ready-to-update` (a container-internal probe addresses the server by container DNS or localhost), `/llms.txt`, the sign-in flow (`/__signin`, `/__signin/callback` and `/__signout`), `/__sso` (bare-site-apex redemption relies on the fallthrough), and the `/npm/*` redirect to `npm.{domain}`. With `BUILDHOST_PRIMARY_DOMAIN` unset the historical fully-host-agnostic behavior is byte-identical, so an IP or localhost deployment is unchanged. The gate is serve-time only. A configured primary domain never changes the route table. `TestPrimaryDomain_UnsetKeepsHostAgnostic` pins both.
